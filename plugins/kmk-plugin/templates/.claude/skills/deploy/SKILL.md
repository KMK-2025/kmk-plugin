## الخطوة 0 — تحديد الوجهة

- `staging` (أو كتبها «تجربة») ← الموقع التجريبي (لا يراه أحد من الناس)
- `production` (أو كتبها «حقيقي») ← الموقع الحقيقي على الدومين
- `mobile` (أو كتبها «جوال») ← إصدار جديد من تطبيق الجوال: اذهب إلى قسم «نشر تطبيق الجوال» في آخر هذا الملف

إن لم يحدد وجهة، اسأله:
> "على وين تنشر؟
> **`/deploy staging`** = نسخة تجربة خاصة فيك عشان تشوف الشغل قبل ما يشوفه الناس
> **`/deploy production`** = الموقع الحقيقي اللي يستخدمه الناس فعلًا"

---

## الخطوة 1 — الفحص الإلزامي

نفّذ بالترتيب، وتوقّف عند أول فشل:

```bash
cd frontend && npm run check         # أنواع + فحص + تنسيق + اختبارات
cd frontend && npm run build         # البناء ينجح
cd backend && ./vendor/bin/pint --test && ./vendor/bin/phpstan analyse && php artisan test
```

ثم تحقق:
- لا يوجد ملف `.env` ضمن التغييرات
- لا توجد كلمات سر أو مفاتيح مكتوبة داخل الكود
- `git status` نظيف

**عند أي فشل، توقف فورًا** وقل له بلغة بسيطة:
> "ما قدرت أنشر. في مشكلة: <الشرح بالعربي>. تحب أصلحها؟"

---

## الخطوة 2 — المراجعة الأمنية

شغّل الوكيل `code-reviewer` على التغييرات.
إن كانت النتيجة تحوي أي بند 🔴 **يمنع النشر**، اعرضه عليه بلغة بسيطة وتوقّف.

---

## الخطوة 3 — إن كانت الوجهة "حقيقي"

1. تحقق أن نفس النسخة نُشرت على التجربة وجُرّبت. إن لم تكن، ارفض وقل:
   > "لازم ننشر على التجربة أول وتجرّبها بنفسك. اكتب: `/deploy staging`"
2. اطلب منه أن يكتب كلمة **انشر** حرفيًا للتأكيد.
3. لا تتابع قبل أن يكتبها.

---

## الخطوة 4 — التنفيذ

1. ادفع إلى الفرع المناسب (`staging` أو `main`).
2. راقب سير GitHub Actions حتى ينتهي.
3. إن فشل، اقرأ سجل الخطأ واشرح السبب بلغة بسيطة.

---

## الخطوة 5 — التسليم

> "تم النشر ✅
> الرابط: https://...
>
> افتح الرابط وتأكد من:
> 1. الصفحة تفتح وتسجيل الدخول يشتغل
> 2. آخر شي أضفناه ظاهر
> 3. جرّبه من جوالك كمان
>
> لو في مشكلة، اكتب `/go-back` وبنرجع للنسخة السابقة فورًا."

# نشر تطبيق الجوال — `/deploy mobile`

إصدار جديد من التطبيق يصل للمختبِرين. **الخدمات تُنشر أولًا دائمًا**: تطبيق جديد على خدمات قديمة ينكسر.

1. **الخدمات منشورة؟** إن كان في الخدمات تغييرات لم تُنشر على الوجهة التي سيتصل بها التطبيق، انشرها أولًا (`/deploy staging` أو `/deploy production`).
2. **الفحص الإلزامي** — توقّف عند أول فشل:
```bash
. ~/.kmk-mobile-env 2>/dev/null; cd mobile && flutter analyze && dart format --set-exit-if-changed lib test && flutter test
cd backend && ./vendor/bin/pint --test && ./vendor/bin/phpstan analyse && php artisan test
```
3. **نسخة الـ API — آليًا، بلا سؤال صاحب المشروع.** إن فشل `ApiShape` فالخدمات تغيّرت بما يكسر الإصدارات القديمة: أعد النسخة القائمة كما كانت، شغّل `bash .claude/scripts/bump-api-version.sh "السبب"`، انقل التغيير للنسخة الجديدة، وانشر الخدمات. إن لم يفشل، الإصدار الجديد يبقى على النسخة الحالية.
4. **ارفع رقم الإصدار** في `mobile/pubspec.yaml` (`version: 1.2.0+5` ← الجزء الثالث +1 لإصلاح، الثاني لميزة؛ والرقم بعد `+` يزيد واحدًا دائمًا)، وحدّث `latest` في `backend/config/mobile.php` لنفس الرقم.
5. شغّل `code-reviewer`. أي بند 🔴 يوقف النشر.
6. **انشر:** احفظ، ثم ادفع الوسم `mobile-v<الإصدار>`. سير `mobile-release` في GitHub يبني التطبيق ويوزّعه على المختبِرين. راقبه حتى ينتهي، وإن فشل اشرح السبب بلغة بسيطة.
7. **سلّم:**
> "الإصدار 1.2.1 من التطبيق طلع ✅
> المختبِرون بيوصلهم إشعار بالتحديث.
> اللي عندهم الإصدار القديم بيكمّلوا شغل عادي لحد ما يحدّثوا."

**لإجبار الجميع على التحديث** (فقط إن طلب، أو قبل حذف نسخة API قديمة): ارفع `min_supported` في `backend/config/mobile.php` وانشر الخدمات. اشرح له الأثر أولًا: "كل اللي عندهم إصدار أقدم من كذا ما بيقدروا يشتغلوا لحد ما يحدّثوا. متأكد؟"
